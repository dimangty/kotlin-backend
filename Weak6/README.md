# Неделя 6. Транзакции, ACID, MVCC и уровни изоляции

**Результат недели:** до запуска эксперимента можешь предсказать, какие версии строк увидит каждая транзакция и какая аномалия допускается на выбранном уровне изоляции. Аномалия считается усвоенной только после того, как воспроизведена вручную двумя сессиями.

Теория недели: [THEORY-SHORT.md](THEORY-SHORT.md) (шпаргалка) и [THEORY-DETAILED.md](THEORY-DETAILED.md) (подробный разбор). Spring-версия недели с теми же сценариями в сервисном слое — [Weak6-1](../Weak6-1/).

## Теория и где она лежит

| Тема плана | Где воспроизводится |
|---|---|
| Non-repeatable read в Read Committed | секция 1 `session-a.sql` / `session-b.sql` |
| Lost update через read-compute-write | секция 2 обеих сессий |
| Безопасное списание: atomic conditional UPDATE | секция 3 обеих сессий |
| Стабильный snapshot в Repeatable Read | секция 4 обеих сессий |
| Serialization failure и retry всей транзакции | секция 5 обеих сессий |
| Инвариант, который держит база | `CHECK (balance >= 0)` в `setup.sql` |

## Запуск

Нужны **две** параллельные psql-сессии — откройте два терминала:

```bash
docker compose up -d
docker compose exec postgres psql -U study -d isolation
```

Если порт 5432 занят другой базой:

```bash
PG_PORT=55432 docker compose up -d
```

`setup.sql` применяется при первом старте: два счёта по 1000, общий инвариант `total = 2000`. Полный сброс — `docker compose down -v`.

## Порядок работы

Выполняйте `session-a.sql` (терминал A) и `session-b.sql` (терминал B) **по одному statement**, строго в порядке комментариев-подсказок. Для каждого из пяти опытов зафиксируйте:

1. timeline: какая сессия что выполнила и в какой момент;
2. какой snapshot видела каждая транзакция;
3. итоговое значение и то, сохранился ли инвариант.

## Задания

1. Пройти все пять секций и оформить timeline каждой аномалии (текстом или схемой) — это артефакт недели для ментора.
2. Секция 2: объяснить, почему Read Committed «разрешил» lost update, хотя dirty read невозможен.
3. Секция 3: сравнить atomic UPDATE с вариантом `SELECT ... FOR UPDATE` + отдельный UPDATE — реализовать второй способ самостоятельно и назвать различия (round trips, время удержания блокировки, место для бизнес-проверки).
4. Секция 4: повторить опыт, но в session A выполнить `UPDATE` той же строки после изменения из B — объяснить полученную ошибку/поведение Repeatable Read.
5. Секция 5: получить SQLSTATE `40001`, затем повторить проигравшую транзакцию целиком и убедиться, что повтор проходит. Объяснить, почему повторять только последний `UPDATE` недостаточно.

## Что разобрать с ментором

- Каждая аномалия по timeline двух транзакций: где именно «разошлись» snapshot'ы.
- Где должна начинаться транзакция в сервисном слое и почему «одна транзакция на HTTP-запрос» — плохой дефолт.
- Какие ошибки можно retry автоматически (`40001`, deadlock `40P01`), а какие нельзя (нехватка средств, ошибки валидации).

## Критерий готовности

- Предсказываешь видимость строк **до** запуска эксперимента, а не объясняешь задним числом.
- Воспроизвёл все пять сценариев руками и можешь повторить любой без подсказок из файлов.
- Понимаешь, какие ошибки нужно retry всей транзакцией, а какие повторять нельзя.

## Контрольные вопросы

- Может ли Read Committed потерять обновление? Почему это не считается нарушением уровня изоляции?
- Чем Repeatable Read отличается от Serializable в PostgreSQL?
- Почему retry должен повторять всю бизнес-транзакцию, а не последний statement?
- Почему atomic `UPDATE ... WHERE balance >= 100` безопасен в Read Committed, хотя две транзакции выполняют его одновременно?
