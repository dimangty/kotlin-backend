# Ревью кода DBAppWeb

Дата: 8 августа 2026 года.

## Итог

Критических, высоких и средних дефектов после исправлений не осталось. Web- и Desktop-клиенты, параллельный REST API, Docker image и все 44 PostgreSQL-сценария проверены. Архитектура соответствует учебной задаче: клиентские приложения выполняют HTTP fan-out, не получают доступ к JDBC, а Spring Boot синхронизирует запросы и явно управляет несколькими соединениями и транзакциями.

## Найдено и исправлено

### Высокий приоритет: Wasm UI открывался пустым

Пользовательский `index.html` не подключал webpack entrypoint. Сборка была успешной, но браузер показывал только фон. Добавлен явный `<script src="dbappweb.js"></script>`, после чего стартовый экран и навигация проверены во встроенном браузере.

### Высокий приоритет: volume PostgreSQL 18 монтировался по старому пути

Официальный образ PostgreSQL 18 требует mount на `/var/lib/postgresql`, а не `/var/lib/postgresql/data`. Старый путь приводил к бесконечному restart/unhealthy. Путь и имя volume исправлены под версионную структуру PostgreSQL 18.

### Средний приоритет: порт API конфликтовал с другим локальным сервисом

Порт `8080` уже использовался другим контейнером. Внешний порт изменён на `18082`, внутренний порт Spring Boot оставлен `8080`. Порты API и БД дополнительно привязаны к `127.0.0.1`, поэтому лаборатория не выставляется в локальную сеть.

### Средний приоритет: несовместимые Kotlin/Wasm metadata

Ktor 3.5.1 был собран с Kotlin/Wasm 2.3.21, а Compose-проект использует Kotlin 2.3.10. Выбран совместимый Ktor 3.3.3; клиент после этого компилируется и проходит браузерный Wasm-тест.

### Средний приоритет: декоративные Unicode-маркеры не входили в Wasm-шрифт

Стрелки и символы статуса отображались пустыми квадратами. Видимые маркеры заменены на `->`, `<-`, `[OK]`, `[EXPECTED]` и `[ERROR]`; клиент также нормализует ответы старого API.

### Предотвращённый риск: параллельные вкладки меняют один стенд

Сценарии сбрасывают общие таблицы перед запуском. Добавлена серверная сериализация через `ReentrantLock`, поэтому одновременно выполняется ровно один пример.

### Предотвращённый риск: каталоги клиента и бэкенда расходятся

Добавлены три уровня проверки: 44 уникальных id в клиенте, точное совпадение реестра JDBC с backend-каталогом и Gradle-задача `verifyCatalogParity`, сравнивающая обе копии каталога между проектами.

### Низкий приоритет: Java toolchain выдавал deprecation warning

Добавлен Foojay resolver для воспроизводимой установки Java 21 на машине с JDK 17. Чистый Docker builder использует Temurin 21.

### Низкий приоритет: комментарий реестра блокировок содержал устаревшее количество

Реестр обслуживает восемь примеров блокировок и три примера дедлоков. Русский комментарий приведён в соответствие с фактическими 11 JDBC-сценариями.

## Дополнительное ревью Desktop-версии

### Предотвращённый риск: платформы могли разойтись в REST-контракте

GET/POST-запросы вынесены в общий `KtorDemoApiClient`. Платформенные классы выбирают только транспорт: Fetch для Wasm и CIO для JVM. Добавлен общий тест с `MockEngine`, который проверяет URL, методы и десериализацию на обоих таргетах.

### Низкий приоритет: общий заголовок называл только Wasm

При визуальном запуске `.app` была замечена подпись `Compose Multiplatform/Wasm`. Она заменена на `Web/Desktop`, чтобы Desktop-окно не описывало себя как браузерное.

### Низкий приоритет: Ktor запускался без SLF4J-провайдера

Первый запуск готового `.app` печатал предупреждение SLF4J о NOP-реализации. В desktop runtime добавлен `slf4j-simple`; повторный запуск прошёл без предупреждений.

### Низкий приоритет: платформенные реализации расширяли публичный API модуля

Общий Ktor-клиент и обе транспортные обёртки отмечены `internal`: они остаются доступны точкам входа и тестам, но не становятся случайным внешним контрактом приложения.

## Ревью параллельного API

### Предотвращённый риск: два HTTP-запроса могли дважды изменить учебную БД

Оба участника встречаются на `CountDownLatch`, после чего `AtomicInteger.compareAndSet` выбирает ровно одного исполнителя. Второй MVC-поток ждёт общий `CompletableFuture`. Unit-тест запускает участников на двух реальных потоках и проверяет единственный вызов JDBC-исполнителя.

### Предотвращённый риск: последовательная клиентская реализация выглядела бы параллельной только по логам

Fan-out вынесен в `executeParallelParticipants`: два `async` создаются до общего `awaitAll`. Отдельный корутинный тест ставит собственный барьер и завершится только после фактического старта обоих участников. MockEngine независимо проверяет два POST-пути, единый `runId` и объединение JSON-ответов.

### Предотвращённый риск: зависшие или смешанные серверные запуски

`runId` ограничен 32 шестнадцатеричными символами, обязательны ровно два разных участника, а пример проверяется до создания состояния. Первый запрос ждёт пару не более десяти секунд. Ошибка завершает общий future, будит второй поток и удаляет state; прерывание MVC-потока восстанавливает interrupt flag.

### Низкий приоритет: SQL-лог мог дублироваться в обоих ответах

Полный журнал сценария возвращает только выбранный исполнитель. Второй ответ содержит регистрацию, открытие барьера и ссылку на номер исполнителя. Клиент сортирует ответы по участникам и печатает SQL ровно один раз.

### Средний приоритет: неизвестный маршрут возвращал HTTP 503

Общий exception handler перехватывал Spring `NoResourceFoundException`, поэтому удалённый последовательный endpoint выглядел временно недоступным. Добавлен отдельный mapping на HTTP 404; неправильное число участников возвращает HTTP 400.

## Остаточные ограничения

- Production bundle Compose Canvas и Skiko заметно больше обычного DOM-приложения; при публикации нужен HTTP compression и длительный cache для хешированных `.wasm`.
- Локальный `.app` не подписан и не notarized. Для распространения вне машины разработчика понадобятся сертификат Apple Developer ID, подпись и notarization; Windows/Linux-пакеты собираются на соответствующих ОС.
- API намеренно не имеет аутентификации и предназначен только для loopback-разработки. Не меняйте bind на внешний интерфейс без security layer.
- Координатор хранится в памяти одного Spring Boot-процесса и синхронно занимает два Tomcat-потока на время примера. Для production-кластера понадобились бы общий Redis/БД-координатор и асинхронный HTTP-контракт; для локальной учебной лаборатории текущая схема проще и нагляднее.
- Планы `EXPLAIN` зависят от статистики, кеша и машины. Тесты проверяют успешное выполнение и наличие реального плана, а не принуждают cost-based planner к одному имени scan node.
